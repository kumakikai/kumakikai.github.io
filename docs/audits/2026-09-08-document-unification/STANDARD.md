# Phase 2 — KUMAKIKAIドキュメント標準

2026-09-08のユーザー依頼に基づく4種文書の統一仕様。既存69ページを更新し、未設置5製品に日本語Termsを追加する。合計74文書。既存の翻訳をすべて更新し、新たな未翻訳ページは日本語と明示して案内する。Apple側の使用許諾・購入条件をサイトの独自Termsで置き換えない。

## 役割と共通骨格

| 種類 | 標準構成 | 全製品共通 | 条件付き/固有 |
| --- | --- | --- | --- |
| 使い方 | はじめに → 基本的な使い方 → 各機能 → 高度な機能・補足 → 困ったとき → お問い合わせ | 概要・対応環境、最初の操作、FAQへの問題解決案内、正式窓口 | 実在する操作・画像・権限・バックアップ・購入等 |
| FAQ | はじめに → 固有の質問群 → データについて → 購入について → 困ったとき | 概要/対応環境、末尾の「不具合が発生した場合は？」「お問い合わせ先は？」 | データ/購入等は利用者に意味がある場合だけ。固有トラブルは共通2問より前 |
| Privacy | はじめに → 取得する情報 → 情報の利用目的 → 情報の保存・管理 → 外部サービス・第三者提供 → 固有処理 → 利用者によるデータ管理・削除 → 未成年者 → 本ポリシーの変更 → お問い合わせ | 運営者/対象、取扱情報・目的・保存・外部処理・管理/削除・変更・窓口 | AI、音声、広告/解析、家族共有、保持期間表、未成年者は実際の処理/利用条件に必要な場合のみ |
| Terms | 適用 → 利用条件 → 禁止事項 → 有料機能・購入 → 固有の利用条件 → 知的財産権 → サービス内容の変更・停止 → 免責事項 → 本規約の変更 → 準拠法・管轄 → お問い合わせ | 利用者/運営者、利用条件・禁止事項・権利・変更/責任・法令・窓口 | 有料機能、サブスク、AIの出力、家族通信、外部特典/ニュース、医療用途の制約等 |

機能がない製品にAI・バックアップ・サブスクリプションの章を追加して項目数を揃えない。構成順と主題単位を揃え、固有機能の見出し・画像・手順は製品に合わせる。FAQに長い法務説明を複製せず、必要なときにPrivacy/Termsの意味が合う節へ参照する。

## 文体・運営者・日付

- 日本語の正式呼称は「本アプリ」「利用者」「当方」「利用規約」「プライバシーポリシー」「お問い合わせ」。引用する画面/ボタン名は実UIを維持する。
- 法務冒頭で「Yuya Nakamuraが運営するアプリ開発ブランドKUMAKIKAI（以下『当方』）」を明示。法人扱い・未確認の漢字氏名/住所を追加しない。翻訳でも同じ主体を表す。
- 法務h2は `1. 見出し` の連番、下位説明は必要時だけh3。使い方/FAQは共通章と固有の操作/質問を区別し、製品によってだけ付いていた章番号は整理する。
- 全対象の改定を `lastmod: 2026-09-08` に記録し、ページ上部に1回だけ表示する。法務は「最終改定日」、使い方/FAQは「更新日」。ISO日付を使用する。
- 確認できる既存制定日は `legal_established` に移し、上部に表示。既存文書の不明な制定日をGit履歴や最終更新日から推定しない。新設Termsは新規制定日を記録する。
- 共通の連絡・問題確認・法務の基本条項は共通shortcode/dataから出力して表記の再分岐を防ぐ。製品の事実は各文書に記述する。

## 問い合わせとナビゲーション

- `data/apps.json.support` と `data/support.json` を正式窓口の唯一の定義とする。ギガポケはアプリと既存法務にある正式フォームをProductにも揃える。フォームを使用する製品は開けない場合の共通メールを併記し、メールの製品は同じメール導線を使う。
- 法務本文の問い合わせは最後の1節。リンク一覧として使い方/FAQ/別法務を再掲しない。法務下部の汎用サポート一覧は表示しない。ページ上部から該当ProductのSupportへ戻れる。
- 使い方とFAQは共通の問い合わせを末尾に置く。共通サポート欄の問い合わせリンクは本文と同一なら省き、残る文書への導線を維持する。
- Product下部は使い方・FAQ・お問い合わせ・Privacy・Termsの5項目を維持する。Products一覧のProduct先頭と `#support` は役割が異なるため両方保持する。
- 同一ページの重複はquery/fragmentを含む完全URLで検出し、ラベルと参照節の意味を確認する。文脈のあるFAQ/法務参照とグローバルナビを機械的に削除しない。

## 内容の判断基準

- 「端末内保存」とAI/同期/広告/フィード/問い合わせの通信を区別する。「一切外部送信しない」は例外が存在する製品では使用しない。
- 実際に情報処理するAWS/Google/Apple等を記載し、サイト生成・リポジトリ・ホスティングの内部事情はアプリの法務から除く。
- 利用者が送った問い合わせ情報は対応に必要な情報として説明する。自動収集と手動で送る情報、アカウント登録と内部の認証/購入識別子を混同しない。
- 期間のある保存・削除後例外は短文化のために消さない。実装既定値を本番運用確認済みと表現しない。確認できない契約/手動削除運用は監査の要確認欄へ残す。
- 買い切り・消費型・自動更新を分ける。価格や試用期間を未確認の固定値にせず、購入画面で確認すべき条件を記載する。アプリ削除とサブスク解約は別であることを該当製品に明記する。
- 共通免責は動作条件・限界を説明し、当方に法令上の責任がある場合まで免除しない。故意/重大な過失の責任、消費者の強行法上の権利を制限しない。
- 改定は内容と適用日を適切に周知し、法令上同意が必要な変更は同意を得る。既存の「掲載だけで無条件に即時適用」を一律再利用しない。

## 検証と保護

既存URL・alias・canonical・翻訳関係・画像を維持する。旧見出しIDは意味が対応する新節に残す。古いIDをすべて先頭へ集めない。Newsの歴史的本文を今回の統一対象に含めない。

元の `docs/migration/baseline.json` は取り直さない。今回明示的に承認された各文書のsource/rendered hash・元baseline hash・削除リンクの理由・実装監査の参照を限定したreview記録に残す。無条件に法務保護を外さず、対象外のURLや未レビューの本文変更を拒否する。

Phase 3後に全74文書を横断比較し、全HTMLを再生成・再走査する。公開した場合はActions/Pagesと実URLへのcache抑制curlを使い、ソース→生成物→公開物の一致を確認する。
